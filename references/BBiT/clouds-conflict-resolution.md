# The Cloud: Resolving Conflicts

> **Credit.** Study note in our own words. The Theory of Constraints thinking processes originate with Eliyahu M. Goldratt (the "Evaporating Cloud"). This tool, as used here, follows the Black Belt in Thinking (BBiT) programme ([blackbeltinthinking.com](https://blackbeltinthinking.com/)). The method remains the work of its authors.

## What it is

A cloud maps a dilemma: two actions that cannot both be done, each serving a legitimate need, both needs serving one common goal. The key move is to stop asking "which option?" and ask "why do we want each?" Conflicts sit at the level of actions. The needs behind them rarely clash.

Three conflict types:
- **Personal:** you are torn between two options.
- **Interpersonal:** you and someone else want different approaches.
- **Policy:** what you want to do runs into a rule or norm.

## When to use it in PreSales

- AE wants a quick demo next week; you want discovery first.
- Customer wants a free extended POC; your policy caps POCs at four weeks.
- You are torn between a custom build for one deal and staying on standard product.

## Steps (build right to left)

- [ ] Write the two clashing actions. Check they truly exclude each other.
- [ ] For each action, ask "why?" and write the need it protects. Needs are outcomes, not actions.
- [ ] Write the common goal both needs serve. Make it as specific as honestly possible.
- [ ] Read each link as "In order to [need], we must [action]" (and goal → need).
- [ ] Check each action really harms the opposite need. If not, there is no conflict.
- [ ] Solve: often it evaporates once the needs are clear. Otherwise find an action that meets both needs, or challenge the assumptions (see `injections.md`).
- [ ] For interpersonal clouds, ask about the other side's need before defending yours.
- [ ] For policy clouds, find the need the policy protects and keep that intact.

## B2B example

- Goal: win a profitable, referenceable deal.
- Need A: show value fast (AE) → Action A: demo next week.
- Need B: show *relevant* value (SC) → Action B: complete discovery before any demo.
- Resolution: a 30-minute discovery call this week, followed by a short, focused demo on the two confirmed pains. Both needs are met.

## Common errors

- Actions that could both be done, so there is nothing to resolve.
- Needs written as actions, or actions written as outcomes.
- Starting from the goal instead of the actions, which bends the whole cloud.
- A goal so generic ("successful company") that no link can be challenged.
- "Solutions" that just pick a winner ("the customer is always right").
