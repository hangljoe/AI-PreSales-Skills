# PreSales Leader — RACI reference

A shared RACI matrix for PreSales ↔ Sales ↔ Product/Solutions ↔ Delivery, and a starter table to
adapt. Handbook ch. 22.11.

---

## The four roles

- **Responsible** — the person who does the work. At least one per task; more than one is fine
  if the work genuinely splits.
- **Accountable** — ultimate ownership of the outcome. Exactly **one** person per task, even when
  several people are Responsible. If two people are both marked Accountable, the matrix is wrong.
- **Consulted** — subject-matter experts asked before a decision is made (for example, Product on
  a customisation request). A two-way conversation, not a notification.
- **Informed** — kept in the loop after the fact (for example, Sales on a demo outcome or a
  promised customisation). A one-way notification.

## How to build one

1. List every recurring PreSales task worth assigning (start from the starter table below).
2. List the stakeholder groups involved — this kit assumes PreSales, Sales, Product/Solutions,
   Delivery/PS, and the customer, but trim or extend for the real org.
3. Assign exactly one R, one A, and any number of C and I per task. A cell can be blank.
4. Review it with the groups it names, not just inside PreSales. A RACI nobody outside PreSales
   has seen is a wish list, not an agreement.
5. Revisit on a role change, a reorg, or when the same task keeps stalling on "who owns this".

**Benefits (ch. 22.11):** clear roles, efficient resourcing, better communication, fewer overlaps
and gaps, real ownership. **Challenges:** overcomplication and ambiguity. **Remedies:** keep it
simple, review and refine on a cadence, communicate it openly rather than filing it away.

## Starter matrix — common PreSales tasks

| Task | PreSales | Sales | Product / Solutions | Delivery / PS | Customer |
|------|----------|-------|----------------------|----------------|----------|
| Discovery call | R | A | I | – | C |
| Demo build and delivery | R, A | C | C | – | C |
| PoC execution | R | A | C | I | C |
| OSD authoring | R, A | C | C | I | C |
| Proposal / commercial terms | C | R, A | I | – | I |
| RFP / RFI response | R | A | C | I | – |
| Technical-win handover | R | I | I | A | I |
| Competitive battlecard | R, A | C | C | – | – |
| Renewal / expansion discovery | R | A | I | C | C |
| Hiring loop for a new SC (leader mode) | A | C | – | – | – |

Adjust freely — this is a starting point, not the handbook's own table (the handbook names the
four roles and the building method in 22.11; the task rows are this kit's working defaults).

## Using this in Hiring mode

The hiring loop itself is a task worth its own row: the hiring leader is usually Accountable, the
panel is Responsible for their own interview slot, a peer SC or the leader's own manager is often
Consulted on the final call, and the wider team is Informed once an offer goes out. Reuse the
starter-matrix pattern above rather than inventing a new shape per req.
