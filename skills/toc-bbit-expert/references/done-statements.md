## Done Statements

*Used within PRT (IOs), TT (Expected Effects), and NCN (nodes). Also invoked standalone when someone asks "what does done look like?" or "help me write a done statement."*

A Done Statement describes the **outcome** you want, not the **actions** you take to get there. It answers one question: **what does "finished" actually look like?**

- Written in **present tense**, as if the result already exists
- Focuses on the **effect**, not the task
- Can be verified by someone **outside** the team — measurable or binary
- Leaves room for **any tactic** to reach the outcome (does not prescribe the how)

### The three principles

| Principle | Weak | Strong |
|-----------|------|--------|
| **Outcome over action** | "Develop a user login feature" | "Users can securely and quickly log in to their accounts" |
| **Clarity of purpose** | "The release schedule is published" | "Our users are aware of the features releasing this quarter" |
| **Objectively verifiable** | "Bugs are resolved quickly" | "90% of critical bugs are resolved within 48 hours" |

*Outcome over action is the only non-negotiable principle. The others depend on the level of detail the situation needs.*

### How to write a Done Statement

1. **Picture the task finished.** What is different about the world?
2. **Write in present tense.** "The system is..." not "We will build..."
3. **Make it measurable or binary** where possible — a number or a true/false state.
4. **Leave room for tactics.** Say *what* changes, not *how* to change it.

### Anti-patterns — catch these before accepting any Done Statement

| Anti-pattern | Example | Fix |
|-------------|---------|-----|
| Action dressed as outcome | "We have completed the review" | "The document is approved and aligned with all requirements" |
| Vague outcome | "Customer experience is improved" | "Customer satisfaction score exceeds 8/10 for the onboarding flow" |
| Over-prescriptive | "Using method X, the code is refactored" | "Load time is reduced by 50%" |
| Two goals in one | "The feature is tested and documented" | Split into two separate Done Statements |
| Output confused with outcome | "10 workshops delivered" | "Teams can independently run the three most-used reports without support" |

### Self-check before accepting any Done Statement

- [ ] The end outcome is obvious just from reading it
- [ ] Someone outside the team can confirm it is done
- [ ] It allows any tactic to reach the outcome — not locked to one method
- [ ] It is simple, direct, and free of clutter
- [ ] It is measurable or binary (not "better," "improved," or "more efficient")
- [ ] It states one outcome — not two goals merged into one sentence
