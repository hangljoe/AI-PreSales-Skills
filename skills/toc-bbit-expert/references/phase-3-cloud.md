## Phase 3 — Map the Conflict (Evaporation Cloud)

**Goal: Surface and name the hidden conflict sustaining the root cause.**

Every persistent problem is sustained by a conflict. Not a mistake, not a gap — a conflict. Two actions that both seem reasonable, serving two real needs, that cannot coexist. The Cloud makes this conflict explicit so it can be *dissolved*, not negotiated around.

*If a problem keeps coming back despite repeated fixes, a cloud is always present. The fixes are addressing symptoms, not the conflict.*

### Three types of conflict

| Type | Description | Example |
|------|-------------|---------|
| **Personal** | You are stuck between two options on your own | "Prepare thoroughly" vs "respond quickly to the AE" |
| **Interpersonal** | You and someone else each want a different approach | SC wants full FTD; AE wants to skip straight to demo |
| **Policy** | You want to take an action but it runs up against a rule or norm | Want to run a free PoC but policy requires VP approval |

### The five elements of the cloud

| Element | Symbol | Question to identify it | Example |
|---------|--------|------------------------|---------|
| **Goal** | G | What do both sides ultimately want to achieve? | "Shorten the sales cycle without losing deal quality" |
| **Need A** | NA | What does Side A need in order to achieve the goal? | "Speed — get to proposal and close quickly" |
| **Need B** | NB | What does Side B need in order to achieve the goal? | "Completeness — full technical discovery before committing" |
| **Want A** | WA | What action does Side A take or push for? | "Skip or compress discovery calls" |
| **Want B** | WB | What opposing action does Side B take or push for? | "Run a full 2-hour FTD before any demo" |
| **Conflict** | ↔ | Why can WA and WB not coexist? | Both compete for the same time in the pre-demo week |

### How to build the cloud — work right to left

1. **Start with the two actions in conflict.** These are what you feel stuck on. Word them as real actions, not beliefs or outcomes. They must directly clash — you can do one or the other, not both.
2. **Add the need behind each action.** Ask: "Why do I (or they) want this?" The need is the real driver — protect it even when you compromise on the action.
3. **Add the common goal that ties both needs together.** This is most important in interpersonal conflicts — it shows both sides why you're even discussing this.

*Tip: for interpersonal conflicts, ask about their side first before defending yours. Once both "whys" are clear, it stops being "my side vs. your side" and becomes both of you solving one situation.*

### Cloud diagram structure

```
                      [G — Goal]
                    /              \
              [NA — Need A]    [NB — Need B]
                   |                  |
            [WA — Want A] ←——→ [WB — Want B]
                         CONFLICT
```

**Every arrow carries an assumption.** State the assumption on each of the five arrows:

| Arrow | Assumption to state |
|-------|-------------------|
| G → NA | "To achieve [G], we need [NA] because..." |
| G → NB | "To achieve [G], we need [NB] because..." |
| NA → WA | "The only way to satisfy [NA] is [WA] because..." |
| NB → WB | "The only way to satisfy [NB] is [WB] because..." |
| WA ↔ WB | "[WA] and [WB] cannot coexist because..." |

### Three ways to solve a cloud

1. **It evaporates.** Once both "whys" are clear, the answer becomes obvious — common with personal and interpersonal clouds.
2. **A bit of thought.** Ask: how can I keep both needs while tweaking the action? Modify the action so it serves both sides. "Walk while taking calls" serves both exercise and time-saving.
3. **Formal injection process.** For stubborn conflicts — use the Phase 4 injection process on the cloud's assumptions. Break your own side first, not the other person's.

### Challenging the assumptions

For each assumption, ask:

- **"Is this always true — or just usually true?"**
- **"Is this a fact or a belief?"**
- **"What would need to change for this to be false?"**
- **"Has it ever been false? Under what conditions?"**
- **"Who decided this was necessary? When? Is that context still valid?"**

*The assumption that, when broken, makes the conflict disappear is your injection target.*

### Common errors when building a cloud

| Error | Fix |
|-------|-----|
| The two actions can both be done at once | Reword so they directly clash — you can do one or the other, not both |
| Needs are worded as actions | Write the true driver behind each action ("ensure quality", not "don't give a due date") |
| Actions are worded as needs | Write what you can actually do right now, not an outcome |
| One action doesn't actually harm the other need | Check that each action genuinely impacts the opposing need — if not, there's no real conflict |
| Goal is too generic | The goal must cover both needs but be as specific as possible — "successful sales team" beats "success" |
| Jumping to the goal first | Always work right to left: actions → needs → goal |

### Druid loop — for oscillating conflicts

If the same conflict keeps returning after being "resolved," you are in a Druid loop. This only applies to problems that come up again and again — if a real solution existed, it would have been found.

**How to build the druid:**

1. **Find the behaviour pair.** Two mutually exclusive behaviours you keep switching between. Word them as behaviours (things you actually *do*), not concepts. "Get involved in quality reviews" is a behaviour; "quality" is not.
2. **Build the first branch.** Pick the side you know best. Write the cause-and-effect steps: "If I do [behaviour], then [effect], then [effect]..." up to the goal violation that drives you to the other side.
3. **Validate the goal violation.** The negative must be strong enough to actually push you to change behaviour. A mild inconvenience won't do it.
4. **Build the second branch.** Same process for the other behaviour. This side is often harder — it requires honestly mapping the problems your own preferred behaviour causes.

```
[Goal is violated — Side A]              [Goal is violated — Side B]
         ↓                                          ↓
[Intermediate effect A2]              [Intermediate effect B2]
         ↓                                          ↓
[Behaviour A] ←————————————————————————→ [Behaviour B]
       (Push back to B when A's            (Push back to A when B's
        goal violation hits)                goal violation hits)
```

**Druid validation checklist:**
- [ ] Both base entities are actual behaviours, not concepts or outcomes
- [ ] You can't do both at the same time (mutually exclusive)
- [ ] Every cause-and-effect link is valid — pull any two boxes out and check
- [ ] Both sides are actually happening right now (not just feared)
- [ ] Each goal violation is serious enough to genuinely drive a switch
- [ ] The loop makes sense: each goal violation raises pressure toward the opposite behaviour

**Druid common errors:**

| Error | Fix |
|-------|-----|
| **Repetition** | Two connected boxes say the same thing with different words — delete the redundant step |
| **Premature looping** | The goal violation includes the other behaviour ("so I go back to...") — stop at the negative, not the response |
| **Failed solution** | One side is the "solution" and its only downside is that it doesn't work — a druid needs two real competing approaches with distinct negatives |
| **Tangent** | Step-by-step drifted to a different theme, so the goal violation no longer connects to the starting behaviour — compare top and bottom entities |
| **Stopping short** | Ended before the negative that actually triggers the switch — go one more step |

After completing: offer to generate a **Druid Excalidraw diagram** — two behaviour nodes at the bottom, cause-and-effect steps rising from each, goal violations at the top, loop arrows showing the back-and-forth.

Break the loop by finding which need is violated at the trigger point and targeting the injection there. Addressing the reactive action directly just accelerates the loop.

After completing: offer to generate a **Cloud (Assumption Graphic) Excalidraw diagram** — all 5 nodes in the standard cloud layout, with assumption text on every arrow.
